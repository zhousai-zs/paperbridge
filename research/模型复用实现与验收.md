# 批次内模型复用：实现边界与验收

## 实现范围

本轮实现性能方案第一阶段。一个 CLI / 桌面转换批次拥有一个惰性启动的引擎子进程，任务顺序执行；相同模型可跨分段及跨文件复用。单独调用 `convert()` 时由它创建并关闭自己的会话；批量 CLI 显式共享同一个 `EngineSession`。

- 模型、精度、输入分辨率、Standard 默认模式及 20 页默认分段保持原设置。未增加 GPU 后端、推理并发或线程数默认值调整。
- 每个分段保留独立素材、日志、检查点和页码检查；模型复用不等于复用文档解析对象。每次任务重新调用 parse，写完素材后释放本次结果并执行垃圾回收。
- 引擎异常、超时或校验失败后丢弃当前进程。原有失败分段归档与重试次数规则继续生效；用户停止不触发重试。
- 完成 32 个分段或段末常驻内存达到 4 GiB 时，在下一段开始前重启引擎。这是回收边界，不是单段运行中的硬内存限制；单段仍受超时和取消约束。
- 批次结束关闭引擎；控制进程意外退出时，存活监测会结束引擎。Windows 记录真实 Python PID，覆盖虚拟环境启动器 PID 与实际执行进程 PID 不同的情况。
- 桌面端一次启动一个批次协调进程，通过临时输入清单传递选择，保留用户选取顺序，避免 Windows 长命令行问题。某篇失败后继续处理其余文件，逐篇进度和结果沿用现有窗口。
- `engine-timing.json` 增加进程 PID、进程内任务序号、复用标记、文档释放时间、段末常驻内存及调度总耗时。`report.json` 标注执行模式。首次 parse 包含模型加载；已有日志加载计时可辅助分析，不能把 parse 的全部时间都当作纯模型计算。

IPC 仅用于本批次的本地子进程，使用私有临时目录、启动握手、请求编号、原子响应文件和输入管道；不监听端口，不引入后台服务。引擎保持固定的进程日志句柄，协调器按任务区间保存到各分段日志，同时覆盖 Python 和原生输出，避免切换句柄导致 Windows 原生库缓存失效。

## 对照与回退

```powershell
# 默认复用
.\.venv\Scripts\python.exe -m paperbridge.cli convert "D:\论文" -o "D:\新结果" --offline

# 逐段隔离，用于对照或临时回退
.\.venv\Scripts\python.exe -m paperbridge.cli convert "D:\论文" -o "D:\另一个新结果" --offline --engine-mode isolated

# 四份固定样本，交错两种模式，每种两轮；必须使用不存在的新目录
.\.venv\Scripts\python.exe scripts/benchmark_engine.py `
  tests/corpus/fixture_en_1col.pdf tests/corpus/fixture_zh_2col.pdf `
  tests/corpus/en_double_math.pdf tests/corpus/bilingual_table.pdf `
  -o .local/engine-benchmark --repeats 2
```

对照脚本拒绝已存在的目标目录，并检查所有分段均未命中结果缓存。相同质量设置、相同文件与页码，交错执行顺序，统计从 CLI 启动到退出的整批时间。比较正文、结构、源文件、原页、证据图和全部检查点内容的 SHA-256；时间、PID 等诊断文件不参与内容比较。

比较一致只能说明此次样本与隔离运行输出相同，不能替代原页对照和识别准确率评估，也不能外推整批复杂论文的提速比例。原始性能分析见 [性能瓶颈与保质提速方案](性能瓶颈与保质提速方案.md)。

内容核对结果：

- 所有源 PDF、图片、原页和证据图的字节哈希一致，素材完整性全部通过。
- 两轮复用结果相对首轮隔离结果，仅有一处行内公式 `\phi,` / `\phi ,` 的空格差异，其余正文、结构和表格一致；该空格不改变数学符号或 TeX 含义。对应差异重复出现在派生 JSON 和 Markdown 中，因此严格文件哈希比较没有标为全等。
- 第二轮隔离结果自身还出现页眉 OCR 的 `CASS` / `CRSS` 字母波动；两轮复用结果在此处均与首轮隔离结果一致。说明原引擎重复运行也可能有内容波动，本轮不修订原始识别文本，不宣称识别零误差。
- 所有差异均已限定到上述字段，未发现其余差异。原始清单及逐字段核对记录：`.local/engine-validation/benchmark-verified/benchmark.json` 和 `content-review.json`。本轮没有重跑原先完整 24 篇基准，也未对全部内容做新的语义标注。

## 下一阶段的收敛边界

模型复用主要减少初始化，四份单页样本的 60% 不能说明长论文中的公式推理也快了 60%。下一阶段先测常驻模型之后剩余的成本，再选择计算后端。

1. 固定代表性页组：公式密集（DiTTo）、图表混合（FAPE-IR）、文字/版面较多（HarnessIR），各选择约 3～5 页，保留行内和长公式；加入跨分段样本检查页码/素材映射。统一用新目录，保持相同分段、模型和质量参数。先在当前 CPU 路径进行进程首任务、后续任务和隔离重跑的对照，记录公式数量、推理、初始化、保存、内存及实际设备信息。当前进度条整数秒仅作辅助，子模型耗时的结论需要更精确的计时。
2. 在相同页组上交错比较 4/6/8 个 CPU 计算线程，保持单文件顺序执行。若两个复测轮次无法重现整批收益，或输出出现无法解释的内容变化，不改变默认 4 线程。不混入 batch、GPU 或分辨率变更。[线程参数与调度说明](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)
3. 针对公式模型做独立 GPU 可行性试验，版面模型作为第二候选。先保持同权重和 FP32 输入，明确控制 TF32 等计算选项，检查实际算子设备分配、CPU 回退、传输开销和峰值显存；不得仅凭 provider 名称宣布加速。依赖放在单独的实验环境并记录版本，不直接修改本机已安装客户端或悄悄修补 site-packages。先证明端到端净收益，再考虑可复现的后端适配和 CPU 回退。含自回归控制流的公式图不能直接套用 CUDA Graph 优化。[CUDA 依赖和限制](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)

每次只验证一类变量。验收继续同时覆盖内容差异、原图、完整性、停止、超时、重试和峰值资源；针对超过原引擎自身波动范围的变化，逐项对照原页。候选方案通过后，再执行完整 24 篇回归及打包验收。

本阶段不同时增加多论文并发、不换更小模型、不降低识别分辨率或长度上限，也不增加新的界面开关。下一步的具体交付应先是一份可复现的代表性基准及 CPU 参数对照，然后才是 GPU 实验结论。
