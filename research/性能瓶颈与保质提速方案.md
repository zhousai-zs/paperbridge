# PaperBridge 性能瓶颈与保质提速方案

分析日期：2026-10-22。基于 main、已发布的 0.3.1、历史 24 篇 / 484 页转换日志及本机依赖源码。第一阶段的批次内模型复用已在源码实现，见 [实现与验收](模型复用实现与验收.md)；已安装客户端尚未替换，GPU 加速仍是后续方案。

## 1. 主要结论

主要耗时是模型推理，公式识别是最大的已识别单项。批量任务还存在跨分段反复加载模型的问题。优先保留当前识别模型、输入分辨率、公式和表格识别、原页/证据图、完整性校验与失败重试，从模型复用、计算设备和资源调度入手。

本机为 i7-13650HX（14 核 / 20 逻辑处理器）、约 32 GB 内存、RTX 4070 Laptop GPU。显卡型号已通过系统查询确认；本次未可靠取得独立显存容量，规划并发前应读取 GPU 实际可用显存，不采用 Windows CIM 的 32 位 AdapterRAM 值推断。

## 2. 时间花在哪里

以下表格固定使用此前 24 篇的历史快照，避免把后来新增的论文或缓存重跑混入统计。

| 项目 | 耗时 | 占总耗时 |
| --- | ---: | ---: |
| 全部转换 | 3025.26 秒 / 50.42 分钟 | 100% |
| 引擎推理整体 | 2648.45 秒 / 44.14 分钟 | 87.54% |
| 公式识别，属于推理内部 | 约 1237 秒 | 40.89% |
| VLM 视觉识别，属于推理内部 | 约 485 秒 | 16.03% |
| 版面识别，属于推理内部 | 约 444 秒 | 14.68% |
| OCR 检测与识别，属于推理内部 | 约 127 秒 | 4.20% |
| 推理之外的进程启动、加载、导出等合计 | 376.81 秒 | 12.46% |

推理子阶段来自进度条整数秒，不能作为严格互斥且完备的性能剖析；不得将其与“引擎推理整体”重复累加。未归入子阶段的推理时间还包含预处理、后处理等，需进一步计时。模型加载和推理的准确边界应以各阶段新增计时复核。

DiTTo 是最突出的长尾：总计 605.97 秒，其中公式识别约 476 秒（78.55%）。两段日志分别处理 436 和 270 个公式识别条目，共 706 个，包含行内公式；这与导出的独立展示公式证据图数量不是同一个指标。不能通过少量展示公式图片推断整篇的公式负担。

0.3.1 安装验收的一页英文样本总计 18.00 秒，其中引擎推理 2.686 秒，已记录的 VLM 加载 5.68 秒，分段处理 17.562 秒；素材保存和检查点生成各 0.016 秒。它说明短文档的初始化占比很高，但不能据此推算长论文的比例，也不能把所有剩余时间都称为模型加载。

## 3. 代码层面原因

1. `paperbridge/desktop.py` 的批量循环逐篇启动转换进程；`core.py` 在每个分段调用独立 worker。历史 24 篇共有 35 个分段，正常首次转换需要 35 次引擎进程启动。默认每段 20 页，即使模型相同也重新构造运行时。
2. `worker.py` 每次完成导入、parse、素材保存、检查点生成后退出。MinerU 自身已有进程内模型缓存，但进程退出后不能跨分段/论文复用。常驻设计还应核对 parser 的运行时所有权和关闭流程，不能只取消退出语句。
3. 当前 ONNX 公式、版面、OCR 的通用会话创建函数固定选择 CPU provider。源码环境 ORT 1.31.0 仅列出 CPU/Azure provider；现有客户端打包未包含 CUDA provider。安装 GPU 运行库或设置 device 字符串，均不足以改变源码中固定的 provider 选择。
4. 公式模型是 PP-FormulaNet-Plus-M，当前 ONNX 包装使用 FP32 输入、最多 8 张一批，自回归解码封装在模型图中。它不是完全没有批处理；应测批次效率和算子设备覆盖，避免把“加 batch”当成未经验证的通用答案。
5. 通用 ONNX 线程默认值是 intra-op=4、inter-op=1；环境变量可调整。线程数需要实测，不能因为有 20 个逻辑处理器就全部分配给每个模型。
6. VLM 使用另一条 llama.cpp 路径。安装包包含 `ggml-vulkan.dll`，Engine 默认 n_gpu_layers=99。旧日志未记录实际 offload 设备，因此只能确认通用 ONNX 路径使用 CPU，不能断言整个客户端从未使用显卡。

## 4. 推荐实施顺序

### 第一阶段：建立可靠对照，复用模型

- 以 0.3.1 冻结版本为基线，记录模型文件哈希、引擎/运行库版本、实际 provider、线程数、批次大小、输入分辨率和质量参数。
- 增加每段的进程启动、模型初始化、各推理阶段、保存、校验计时；记录峰值内存/显存、公式数量及长度分布。区分第一次启动、模型已加载但尚未转换过的文档、已完成结果复用三种情况。
- 在受控负载下交错测试 4/6/8 个计算线程，分别覆盖公式、版面、VLM，选择整批总耗时较好的配置。当前小样本发现明显运行时波动，不应直接发布某个固定线程数。
- 引入一个批次内常驻的引擎子进程，初版仍逐段处理任务，加载模型后跨段跨篇复用。保留 20 页检查点、独立输出目录、原子完成标记、页码覆盖和素材校验。
- 主进程保留超时与取消控制。引擎卡死或用户停止时结束该引擎进程，重启后只重试未完成分段；记录异常，设置内存上限和任务间安全回收点。不能为了常驻而失去可靠停止能力。
- 缩短重复导入/初始化主要改善短篇及批量体验。按旧报告口径，推理之外全部时间仅约 6.28 分钟；只优化这部分，即使理想化地全部消除也远达不到整体翻倍。

### 第二阶段：使用本机 GPU 加速主要推理阶段

- 优先对公式和版面模型做独立 CUDA 试验；公式占比最大，版面模型也值得同时纳入候选，以实际算子覆盖和净收益决定上线顺序。
- 保留模型权重、图像处理、识别长度和后处理规则。先比较相同模型的 FP32 路径；需要精确对照时明确控制 TF32 等计算选项。浮点执行设备变化不保证输出逐字一致，必须比较结果。
- 修改会话工厂并打包相匹配的 GPU 运行库；打印实际算子设备分配、CPU 回退和传输时间，不能用 provider 列表或显卡利用率代替性能证据。
- 公式图内自回归循环和 CPU/GPU 数据传输可能抵消收益。先验证普通 CUDA 执行；若效果差，再评估同权重的其他后端或重构解码。CUDA Graph 不能直接用于含 If/Loop/Scan 的图，不应作为初期默认方案。
- VLM 单独核查实际 Vulkan 设备和 offload 状态；先确认是否已在利用 RTX，再决定是否调整后端或并发。
- 设计 GPU 不可用、显存不足和驱动不兼容时的 CPU 回退，回退使用相同质量设置并明确记录原因。

ONNX Runtime 的 CUDA 依赖、算子执行与 CUDA Graph 限制参见 [官方 CUDA 文档](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)。

### 第三阶段：受控流水线、批次和缓存

- 先尝试让上一段的保存/校验与下一段的推理重叠，避免同时复制多套大模型。任务调度必须限制待写数据量，并在所有输出校验完成后才对用户报告成功。
- 论文级并发从 1、2 个任务测起，统一分配 CPU 线程和显存。多个推理进程各自满线程会产生竞争；本机显存上限实测前不开放高并发。
- 保持现有默认 20 页检查点；20/40/64 页作为后续试验候选。增大分段会增加失败重做量、峰值内存，并可能因批次或上下文变化影响输出；常驻后无需依靠大分段来减少模型初始化。
- 公式批次可测 1/4/8，扩大上限需改后端并重新验收。长短公式分组仅作为待测方案，不减少公式条目，不截断最大识别长度。
- 公式结果去重仅允许对完全相同的预处理输入、模型、前后处理版本和质量配置复用。不可按图片相似度跳过识别，防止把细小上下标差异合并。
- 缓存指纹纳入模型、后端及影响输出的配置；当前作业目录指纹主要包含 PDF、模式、页码、chunk_size 和 MinerU 版本。对照试验必须用独立输出目录或强制禁用旧结果复用，避免把缓存命中误判为模型提速。
- 原页/证据图压缩和重复解码检查可以后置优化；保留图片实际解码、完整性校验和失败重试。线程和推理队列配置参考 [ONNX Runtime 官方线程说明](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)。

## 5. 怎样保证质量

发布准入需要同时满足内容、完整性和可靠性，不能只看 Markdown 能打开：

- 内容：固定文字型、双栏、复杂公式、表格、中文、扫描页及长论文样本；比较文本、阅读顺序、LaTeX、表格单元格、图片与题注关联。公式重点包含行内符号、上下标、分式、长公式。对发生变化的条目逐项对照原页；原有结果不是绝对正确的标注，不能只把“和旧版一样”当成正确。
- 完整性：全部页面覆盖，图片引用存在且实际可解码，源 PDF/检查点哈希一致，证据图与结构映射正确，零新增素材缺失。`integrity.passed` 本身不能证明图都被检测到或公式识别正确。
- 可靠性：连续批量转换、停止、超时、引擎崩溃、显存不足、损坏缓存和失败重试均须通过；观察常驻运行的内存增长和批次后半段速度。
- 性能：相同文件、页码和质量参数；接电并保持一致性能模式，控制后台负载。冷热启动分开、固定样本重复运行，报告总耗时、中位数、尾部耗时和峰值资源，最后重跑完整 24 篇基准。

每次只引入一个主要变量。先常驻，再 GPU，再并发，便于判断收益和定位质量回退。新增计时和校验继续保留。

## 6. 可量化的收益边界

以下仅按历史耗时进行敏感性计算，假设其他阶段完全不变，**不是已实测的提速承诺**：

| 假设 | 24 篇总用时 | 相对原用时减少 |
| --- | ---: | ---: |
| 公式阶段快 2 倍 | 约 40.11 分钟 | 20.4% |
| 公式阶段快 4 倍 | 约 34.96 分钟 | 30.7% |
| 整个推理阶段快 2 倍 | 约 28.35 分钟 | 43.8% |

这说明公式加速有价值，但整体翻倍还需要版面、VLM 和初始化共同改善。保质前提下，最值得投入的是“模型常驻 + 主要 ONNX 模型 GPU 加速”；盲目增加线程或把论文全部并发不应作为默认方案。

## 7. 本次公式线程小试验

使用 DiTTo 已保存的 4 张展示公式证据图、相同 ONNX 模型、batch=4；每个配置独立初始化，执行 3 次，取后两次中位数。它测试的是这些裁片的预处理和公式识别，裁片与原始引擎的全部公式输入并不相同，不是整篇对照试验。

| 配置与顺序 | 4 张裁片处理耗时 |
| --- | ---: |
| 第一轮 4 线程 | 10.79 秒 |
| 第一轮 2 线程 | 16.22 秒 |
| 第一轮 6 线程 | 2.15 秒 |
| 第一轮 8 线程 | 2.05 秒 |
| 随后回测 4 线程 | 2.48 秒 |

共 15 次调用得到的 4 条公式文本完全一致。4 线程的回测从 10.79 秒降至 2.48 秒，模型初始化也从 15.73 秒降至 3.63 秒，说明第一轮存在无法归因于线程数的运行条件差异。后台负载、电源/调度或缓存是待排查因素，本次没有资源时间序列，不能确定具体原因。

**不能把第一轮差距声称为 5 倍提速。** 后半段 4/6/8 线程约 2.48/2.15/2.05 秒，仅提示 6～8 线程值得继续测；尚不足以决定默认值，更不能保证整批论文节省相同比例。下一步应交错重复配置并同步采集 CPU/GPU 使用、频率、进程优先级和内存数据。
