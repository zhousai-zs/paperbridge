# 知识库实战案例：长论文怎样被 Agent 检索、理解和复用

调研日期：2026-10-22。服务于现有 Obsidian 图像复原论文库。

本次查阅公开项目、作者工作流、实际知识库页面和部分实现代码。未安装这些系统，未在本机论文上测准确率、速度或成本；在线演示只确认有入口，没有完成交互验收。下文将项目已公开的行为和针对本库的建议分开。

## 1. LLM Wiki：把读过的资料整理成可持续更新的知识

### 作者实际怎样用

Karpathy 在 LLM Wiki 原始说明中描述：一边开 Agent、一边开 Obsidian；新资料加入后，让 Agent 更新来源摘要、相关概念和索引；有价值的问答再保存为新页面；定期检查过期结论、冲突和断链。文件分为原始来源、生成的 Wiki、维护规则三层。该 Gist 是工作流说明，不是完整软件或效果评测。[作者原始说明](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

### 可以打开成品看的公开库

`jason-effi-lab/karpathy-llm-wiki-vault` 提供一个中文提示工程示例库。其索引包含来源摘要、实体、概念和综合分析；日志记录了摄入资料、根据已有知识生成新笔记、执行检查的过程。可以依次查看：[知识索引](https://github.com/jason-effi-lab/karpathy-llm-wiki-vault/blob/main/wiki/index.md)、[概念页实例](https://github.com/jason-effi-lab/karpathy-llm-wiki-vault/blob/main/wiki/concepts/Context_Engineering.md)、[操作日志](https://github.com/jason-effi-lab/karpathy-llm-wiki-vault/blob/main/wiki/log.md)。

这份成品也展示了维护难点：日志明确列出尚未创建的索引目标、死链和未展开的冲突；所查看的概念页中，一些数值性断言缺少精确原文定位。因此它适合参考文件组织与使用过程，不能直接把其技术结论当作已核验知识。[检查记录](https://github.com/jason-effi-lab/karpathy-llm-wiki-vault/blob/main/wiki/log.md)

### 有代码的实现：oamc

oamc 将这一思路做成 CLI 和本地界面：资料进入收件箱，经过处理形成 Wiki，在 Obsidian 查看，再围绕研究问题查询。它提供 ingest、query、lint、watch 等操作；README 的常驻菜单栏方案针对 macOS，不能据此推定 Windows 上直接可用。[项目与每日流程](https://github.com/michiosw/oamc)

我还检查了它的查询代码：先挑选 Wiki 页面，在字符预算内加载内容，连同索引和规则交给模型；开启保存时，将结果写入综合分析页，重建索引并追加日志。搜索实现使用标题、路径、摘要、正文的加权词项匹配，返回前若干篇；并非必须先搭建向量数据库。[查询实现](https://github.com/michiosw/oamc/blob/main/src/llm_wiki/ops/query.py)、[检索实现](https://github.com/michiosw/oamc/blob/main/src/llm_wiki/ops/search.py)

从代码也能看出限制：相关性排序和字符截断并不证明证据完整；未命中有效词项的候选也可能进入返回集合。这是可以学习的工程实例，不是已经证明适用于中文长论文的完整答案。

**对本库的启发：**除了“AgenticIR 摘要”，还可以按真实需求积累“工具规划”“退化感知”“记忆机制”等概念页，以及“几种规划路线比较”等专题。来源论文保持原位；这些页面是 AI 维护的派生资料，不要求用户手工填卡。

## 2. PaperQA：每个研究问题有自己的证据集合

PaperQA 面向科学文献。项目快速开始示例以一个论文文件夹为输入；公开回答示例展示如何汇总关于 DNA／蛋白质计算的问题，并给出论文及页段引用。[项目与回答示例](https://github.com/Future-House/paper-qa#quickstart)

它公开的默认流程是：

```text
找候选论文
  → 检索相关文本块
  → 围绕当前问题生成证据摘要并评分
  → 选择证据生成带引用的回答
  → 必要时继续搜索或换一种问法
```

关键在于“围绕当前问题”。同一篇文章被问训练成本和被问失败案例时，所需证据摘要不同，不能只依赖一份固定的全篇摘要。[工作流说明](https://github.com/Future-House/paper-qa#usage)

图表处理也值得参考：项目说明将媒体与文本块关联，避免在分块时拆散媒体；可生成辅助检索的图表描述，但将生成描述与原始文字分开。启用该增强会增加模型调用。[多模态说明](https://github.com/Future-House/paper-qa#multimodal-support)

**对本库的启发：**固定理解摘要负责初筛；当用户问“哪种规划方式更节省调用”时，再生成这次问题的证据表，记录工具池、调用预算、成功标准和来源页。公式、图表须通过现有原页入口核对。

完整运行 PaperQA 需要配置模型服务，项目支持云端或本地方式。本次没有替你部署；可以先借鉴证据流程，再决定是否采用整套系统。[模型配置说明](https://github.com/Future-House/paper-qa#installation)

## 3. QMD：给现有 Markdown 文件夹加上可复用的检索入口

QMD 是面向本地 Markdown 的搜索工具，公开了关键词检索、语义检索和混合排序，以及供 Agent 使用的命令行与 MCP 接口。检索和读取分开：先返回候选，再按文档或行范围读取。关键词路径可不调用 LLM；语义与重排路径使用本地模型，并有模型下载及运行成本。[项目与接口](https://github.com/tobi/qmd)

它随项目提供的 Agent 使用说明特别强调：搜索片段只是线索，涉及事实和细节时应取回来源内容，再引用文档及行号。[项目内使用说明，作为调研材料读取](https://github.com/tobi/qmd/blob/main/skills/qmd/SKILL.md)

### 一个明确的接入案例

GitHub Agentic Workflows 的 QMD 实验性功能，为文档单独建立索引，通过 Actions 缓存交给 Agent 任务；也支持从缓存恢复索引、跳过建索引步骤。这是公开集成实例，但文档明确标为实验性，不代表所有 GitHub 产品都这样工作。[集成文档](https://github.github.io/gh-aw/experimental/qmd/)

**对本库的启发：**论文仍然是原有 Markdown 文件。搜索工具替 Agent 找到候选和位置，Agent 再读取相关内容，不需要为每次聊天重新扫描和理解所有全文。

若试用，应分别测试“中文问题找英文正文”和专业缩写检索。QMD 本身不证明实验条件已对齐，也不负责建立可靠的跨论文论断；这些仍由阅读与分析流程完成。

## 4. Copilot for Obsidian：专题工作可以先保存范围，按需读取

当前项目把 Agent 工作放进 Obsidian，并提供 Projects 保存长期任务的规则、上下文和聊天历史。[项目](https://github.com/logancyang/obsidian-copilot)

Projects 文档有一个特别相关的机制：新聊天先获得已保存资料的位置列表，等问题需要时再读取来源。用户可以按文件、文件夹、标签或属性组织上下文；项目规则和资料清单也保存为文件。[Projects 使用流程](https://github.com/logancyang/obsidian-copilot/blob/master/docs/projects.md)

**对本库的启发：**将“图像复原 Agent 规划机制比较”设为一个有明确范围的研究任务，保存比较维度、候选资料入口和输出要求。后续讨论延续这些约束，但按问题展开原文。

这可以先作为交互设计参考。当前已经能用 Agent 访问本地库，不必为了采用这种工作方式马上安装插件。若以后希望所有操作都在 Obsidian 界面内完成，再实测它的当前版本、模型接入和 Windows 支持。

## 5. Kotaemon：让引用成为可操作的证据入口

Kotaemon 提供文档问答 Web 界面，支持文件集合、全文与向量混合检索、重排、问题拆解，并展示带引用的答案及 PDF 高亮预览。项目还提供图表和多模态解析的接入选项。[项目](https://github.com/Cinnamon/kotaemon)

可以查看 [README 中的界面图](https://github.com/Cinnamon/kotaemon#features)，也可以打开项目提供的 [Kotaemon Papers 演示入口](https://huggingface.co/spaces/cin-model/kotaemon)。本次确认了演示入口存在，没有验证在线服务能完成一次上传和回答。

**对本库的启发：**答案中的“论文 A 第 7 页表 2”应该能直接打开对应证据，而不仅是文末列一串论文名。已有的 PDF、原页图和裁片可以继续承担这项功能。

它更适合参考界面和证据展示方式。直接引入会增加独立应用、模型和索引配置，因此是否整体采用应另行评估。

## 6. 延伸案例：GraphRAG 怎样处理全库主题问题

Microsoft Research 公开过利用 VIINA 新闻数据进行跨材料关联分析的研究案例。其全局查询设计先使用预生成的社区报告，再分批形成中间结果并合并，以回答跨整个数据集的主题问题。[研究案例](https://www.microsoft.com/en-us/research/blog/graphrag-unlocking-llm-discovery-on-narrative-private-data/)、[全局查询机制](https://microsoft.github.io/graphrag/query/global_search/)

这提示我们将“某篇的模块怎么工作”和“全库有哪些研究路线”视为不同类型的查询。后者需要覆盖记录和跨组综合。

当前仓库说明项目主要处于维护模式，也提示索引成本可能较高。对 25 篇论文，优先借鉴全局综合思路；本次不建议仅为画关系图引入整套 GraphRAG。[仓库状态与边界](https://github.com/microsoft/graphrag)

## 7. KamaAgenticRAG：从固定检索走向 Agent 自主查证

补充调研日期：2026-10-22。核对版本：`fdeda6b7261cd6e03fbcab930b31f1a780372542`。本节查阅 README、四阶段工作流、检索／分块／来源结构、预算与状态实现，以及相关测试和评测代码；未下载教学数据包、部署服务或运行测试，因此不报告实际问答准确率。

### 定位与评价

仓库名为 KamaAgenticRAG，当前 README 标题为“FlowPay Agentic RAG 教学项目”。它围绕虚构支付公司的客服排障设计，重点是让人看清 Agent 如何选择工具、追查证据和处理多轮条件变化。**作为 Agentic RAG 工程学习样板值得看；用于现有论文库时，更适合借鉴查询执行层。**这是基于以下源码检查的判断。[项目说明](https://github.com/youngyangyang04/KamaAgenticRAG)

### 四阶段分别做什么

| 阶段 | 已核对的实现 | 对论文库的启发 |
| --- | --- | --- |
| s1：朴素 RAG | 结合最近对话检索一次，取 10 个片段，再生成回答 | 建立最简单的对照流程，测清一次检索会漏什么 |
| s2：自主检索 | 模型选择搜索片段或读回整篇；每轮最多 3 次工具调用、5 次模型调用 | 证据不足时允许补搜、展开来源，并限制重复调用 |
| s3：多源排查 | 将文档规则与数据库、日志中的实际记录结合 | 将来可组合论文、代码与复现实验记录，区分作者报告和本地结果 |
| s4：多轮排查 | 累积用户条件，缺条件时追问；条件更正后要求按新条件重查 | 比较任务的退化类型、数据集、预算发生变化时，需要重新检查证据适用性 |

来源：[s1](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/workflows/s1.py)、[s2](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/workflows/s2.py)、[s3](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/workflows/s3.py)、[s4](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/workflows/s4.py)。

### 特别值得借鉴的实现

**1. 搜索与阅读是不同工具。**`search_documents` 返回相关片段和引用 ID；`read_document` 按已知文档 ID 取回全部分块。s2 的提示词明确要求：片段不完整时展开阅读，避免只是反复换词搜索。代码也对相同查询和相同文档的重复调用做限制。[工具定义](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/core/knowledge/tools.py)

**2. 给模型的内容精简，后台来源完整保留。**模型收到片段 ID、标题、正文和相似度；集合版本、源路径、哈希和原文定位留在证据结构及事件记录中。这比把所有管理字段反复塞进上下文更有针对性。相似度用于排序，不能解释为答案正确率。[证据结构与模型载荷](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/core/knowledge/contracts.py)

**3. 记录“为什么停止”。**预算用完被要求收尾，与模型自行判断可以回答，使用不同状态；可记录检索请求、结果、工具调用和累计证据。s2 及后续阶段还可通过检查点保留消息与已读片段。[调用预算](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/core/agent/budget.py)、[轮次状态](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/core/agent/turn.py)

**4. 检查索引与嵌入模型身份。**查询前核对集合及向量模型配置；入库支持从尚未生成向量的块继续处理。适合借鉴到论文索引的版本管理中，但不能把该项目绑定端口等部署细节当成所有向量检索系统的普遍要求。[知识客户端](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/core/knowledge/client.py)

**5. 区分证据覆盖与答案结论。**评测代码分别检查是否获取指定证据、是否覆盖必需断言及触犯禁止结论。断言检查主要使用文本匹配启发式，不等价于完整语义核验；源码包含评测框架不代表已经证明在本库上有效。[评测实现](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/scripts/benchmark/run.py)

### 用于长论文之前，需要补什么

- **数据入口要改造。**默认教学流程依赖单独下发、未随仓库分发的数据包。README 声明其中含 100 篇文档、712 个向量；这是配套数据说明，不是本次实测结果。现有导入程序校验冻结发布清单，并要求 Markdown 元数据；不能把我们的论文文件夹直接当作已兼容输入。[运行要求](https://github.com/youngyangyang04/KamaAgenticRAG#前置条件)、[导入实现](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/scripts/ingestion/corpus.py)
- **分块要适配图和公式。**当前分块先按 Markdown 标题分节，再按字符窗口切割，默认上限来自配置。已读代码没有公式、HTML 表格、图与图注的专门保护，长结构可能被切开。需要接入 PaperBridge 的原页标记与结构信息。[分块实现](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/core/knowledge/documents.py)
- **展开阅读要增加章节粒度与长度预算。**现有 `read_document` 返回全部分块，代码以短业务文档为预期；工具调用次数有限，并不保证输入 token 数有限。论文场景应增加按章节、页段或证据块读取的能力，避免一次展开十余万字符。[整篇读回实现](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/core/knowledge/store.py)
- **检索与综合层仍需扩展。**已核对的存储检索按 pgvector 余弦相似度排序，没有在这条路径中实现关键词与向量融合、重排。对于全库综述，还需另外记录逐篇覆盖；对于长期知识积累，还需建立摘要、概念页和专题的写回维护流程。[检索实现](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/src/flowpay/core/knowledge/store.py)
- **引用可定位与结论被支持要分别检查。**来源结构保留了回查条件，但测试明确允许正文保留未知引用 ID，由界面标识无法定位。不能将它描述为“已经杜绝编造引用”或“自动验证每个断言”。[回答与引用测试](https://github.com/youngyangyang04/KamaAgenticRAG/blob/fdeda6b7261cd6e03fbcab930b31f1a780372542/backend/tests/core/test_answer_contract.py)

### 运行成本与建议阅读入口

README 的默认方案需要 Docker Desktop、聊天模型密钥及教学数据包，使用 PostgreSQL／pgvector 和 Ollama 嵌入服务；文档估算约 8 GB 磁盘。这是一个有前后端的独立教学应用，部署成本高于给现有 Markdown 库加搜索入口。本次未验证 Windows 启动流程。[部署说明](https://github.com/youngyangyang04/KamaAgenticRAG)

建议先看 **s1 → s2 → `knowledge/tools.py` → `knowledge/documents.py` → `agent/budget.py`**。这几处最直接回答“Agent 怎么避免每次读完全部资料”；s3、s4 可在需要多源实验分析和长期研究会话时再看。

对本库的取舍是：**借鉴 s2 的按需查证循环、精简模型载荷、来源追踪和停止状态；补上章节阅读、结构保护和知识写回。** 暂不将更换整个资料管理系统作为前提。

## 看完案例后，对上一版设计的调整建议

上一版的分层读取方向可以保留，但应补充三个要点：

1. **组织知识不能只停在“每篇一个摘要”。**跨论文概念和比较结果也要有可保存的页面；按实际问题逐步生成，避免先创建大量空页面。
2. **固定摘要与问题证据分开。**固定摘要帮助找到论文；具体论断依靠当次检索、原文核对和条件对照。
3. **将“读取与回答”和“写回知识库”分开控制。**普通问答先给结果；只有适合沉淀的结果才更新专题，并保留出处、版本和变更记录。
4. **检索过程本身也要可检查。**参考 KamaAgenticRAG，记录查询、读回范围、累计证据和停止原因；同时为长论文增加 token／字符预算，不能只限制工具调用次数。

一个适合本库的试验问题是：

> AgenticIR、SEAR 和 Causal-AgentIR 的记忆分别保存什么？什么时候更新？怎样影响规划？

试验时只沉淀三类实际产物：相关论文理解摘要、一页带来源的“记忆机制”概念说明、一份比较表。每项重要断言回到原文；不把未检查部分填成不存在。再问一个相邻问题，观察这些产物是否帮助减少重复阅读。

这项试验是调研后的建议，本次没有执行，也没有改变现有库的分类规则或目录。

## 建议的浏览顺序

以下时间为浏览安排估计：

1. **约 10 分钟：**看示例库的索引、一个概念页、操作日志。先理解成品长什么样，以及实际暴露了哪些问题。
2. **约 5 分钟：**看 oamc 的 Daily Flow，理解新资料进入、查询、保存结果的循环。
3. **约 10 分钟：**看 PaperQA 的回答示例和工作流，理解一次具体问题怎样收集证据。
4. **按兴趣继续：**QMD 看检索与缓存；Copilot 看库内操作；Kotaemon 看引用预览；GraphRAG 看全库综合。
5. **想看中文 Agentic RAG 源码：**优先读 KamaAgenticRAG 的 s1、s2，对比固定检索与自主查证，再看分块和调用预算。

推荐先看案例再确定落地组合。无需同时安装这些项目，也无需迁移现有论文资料。
